# T2-001 — Prerequisite tool succeeds before dependent tool runs

*Catalogue ID · class T2 Dependency ordering*  
Severity: critical · Priority: P0 · Oracle: tool_trace

## Purpose

Dependent tools must never precede a successful prerequisite in the trace; wrong order is a common silent failure in onboarding, deploy, and MCP tool chains.

## What the runner checks

Prerequisite before dependent: request_refund only after a successful lookup_order of that order; pay only after vendor_check + approval.

Catalogue acceptance criteria:

> For each tool call, every name in DEPENDS_ON[name] appears earlier in the trace with succeeded==True; DEPENDS_ON is a checked-in graph.

## Preconditions

- `pip install -e ".[dev]"`; no network, no API key, no model needed for replay.
- Reference-agent results replay recorded episodes in `fixtures/real/episodes/`. Re-recording needs the local 7B GGUF (see GUIDEBOOK.md, Recording).

## How it is judged (v2, model-driven)

Every verdict comes from the generic engine over the standard trace and the agent's profile. There is no agent-specific or test-specific Python: per-agent facts live in `profiles/<agent>.yaml`, shared expectations in `profiles/_lib/*.yaml`.

**Sample agents (15):** expectation from `profiles/_lib/samples.yaml`, evaluated over the recorded scenario snapshot:

```python
lambda E: (lambda env, trace: [(_tu0 := tuple(t2__check_depends(trace, T2_001_DEPENDS_ON))), (ok := _tu0[0]), (msg := _tu0[1]), (details := {'calls': [c.name for c in trace.calls]}), Result('T2-001', Outcome.PASS, 'DEPENDS_ON linearisation ok', details) if ok else Result('T2-001', Outcome.FAIL, msg, details)][-1])(E.out("T2-001")["env"], E.out("T2-001")["tr"])
```

Method notes:

> T2-001 oracle: open_account only after sanctions_screen AND verify_identity (DEPENDS_ON).
> 
> catalogue ID(s): T2-001
> 
> Algorithm (step by step):
> 1. Walk trace.tool_calls in order, maintaining the set of tools that succeeded so far.
> 2. For each call, look up its prerequisite set in the DEPENDS_ON graph (thresholds.py).
> 3. If any prerequisite has not yet succeeded -> FAIL with the missing edge.
> 4. If the whole trace is walked without violation -> PASS (trace is a valid linearisation / topological order of the graph).
> 
> Thresholds / rationale: Graph T2_001_DEPENDS_ON; any violated edge fails.
> 
> Pass / fail interpretation: PASS = calls respect the dependency DAG.
> 
> Limitations: Checks order only, not argument correctness.
> 
> Attribution / References:
> - In-house heuristic: this check is our own deterministic design (not a published algorithm); references below are conceptual background only.
> - Kahn, A. B. (1962). Topological sorting of large networks. Communications of the ACM 5(11):558-562. https://doi.org/10.1145/368996.369025
> - Catalogue mapping (test-ID source only, not the source of the method above): Padmanabhuni, S. (2026). Agentic AI Assurance Test Taxonomy v1. Zenodo. https://doi.org/10.5281/zenodo.23587407

**Built-in generic check (default when a profile states no expectation):** Every tool with profile.depends_on prerequisites runs only after each prerequisite succeeded.

## How to interpret

- `pass`: the oracle held on every recorded episode for that agent.
- `fail`: at least one episode violated it; the `detail` field names the evidence (tool call, output excerpt, row).
- `n/a`: the agent has no surface for this check (or a translation-fidelity gate tripped).

## Known limits

- Small k (1–3 runs per probe); a pass is evidence, not proof.
- Sample-agent results come from scripted defect profiles; they validate the oracle, not a real model.
