# T1-001 — Terminal postconditions hold after a single agent task

*Catalogue ID · class T1 Task success rate / terminal state*  
Severity: critical · Priority: P0 · Oracle: terminal_state

## Purpose

After one task run, systems of record must match the expected terminal statuses and no collateral rows may be written. Agent builders need this to catch false "done" claims that leave production data wrong.

## What the runner checks

First canonical run meets its success signal (gen_ai.evaluation.result, or published postconditions), and no run leaves an object in contradictory terminal states (two successful state-changing calls on the same object whose outcomes exclude each other; judge: record-only per tool, then exclusive-outcomes on the tool pair).

Catalogue acceptance criteria:

> For every expected id→status pair, the ledger (or equivalent store) equals that status; store.unchanged_except(expected_ids) is true; runs that claim success while any expected pair mismatches count as false_completion and must be zero.

## Preconditions

- `pip install -e ".[dev]"`; no network, no API key, no model needed to judge recorded traces.
- Each agent is a folder of standard files only: `agent-card.json` (A2A), `tools.json` (MCP tools/list) and `traces/*.otlp.jsonl` (OTel GenAI). See the [User Guide](../USER-GUIDE.md).

## How it is judged (v3, standards-based)

**Universal rule** (`src/agentest/standards/rules.py`, the same for every agent): First canonical run meets its success signal (gen_ai.evaluation.result, or published postconditions), and no run leaves an object in contradictory terminal states (two successful state-changing calls on the same object whose outcomes exclude each other; judge: record-only per tool, then exclusive-outcomes on the tool pair).

Inputs: OTel GenAI spans (OTLP/JSON) + the agent's A2A AgentCard, MCP tool annotations and, where needed, the governance extension `urn:agentest:a2a-ext:governance:v1`. No agent-specific expectation exists.

**Semantic part (LLM judge).** Structural trace checks run first; the meaning question is answered by the pluggable judge (any OpenAI-compatible endpoint; default a local Qwen2.5-7B via llama.cpp; temperature 0, fixed seed, JSON answer, cached) with the versioned scoring guide(s) [`exclusive-outcomes` v1](../../src/agentest/standards/guides/exclusive-outcomes.yaml), [`record-only` v1](../../src/agentest/standards/guides/record-only.yaml). The judge model and guide versions are recorded in each result. Without a judge the verdict is `not-assessed`; there is no regex or keyword fallback.

**Conformance-scenario oracle** (test-owned, `scenarios.yaml`; applies only to the sample-agent fixture runs whose input id is this ID; every other trace is judged by the universal rule above):

```python
lambda E: (lambda env, trace: t1_001_evaluate_t1_001(env, trace, expected=T1_001_EXPECTED))(E.out("T1-001")["env"], E.out("T1-001")["tr"])
```

## How to interpret

- `pass`: the rule held on every recorded trace of that agent.
- `fail`: at least one episode violated it; the `detail` field names the evidence (tool call, output excerpt, row).
- `n/a`: the agent's traces and metadata carry no signal for this check (the detail says which one is missing).
- `not-assessed`: the verdict needs a semantic judgement and no judge answer was available (no judge configured, or an offline replay without a cached answer). It is neither a pass nor a fail.

## Known limits

- Small k (1–3 runs per probe); a pass is evidence, not proof.
- Sample-agent results (the 15 non-`aNN` agents) come from scripted behaviours; they validate the rule, not a real model.
- The bundled judge is an uncalibrated local 7B model with open scoring guides; its answers can be wrong. Results record the judge identity and guide versions so a different or calibrated judge can be swapped in.
